## 4. 知识与检索

- MySQL `faq_entry` 继续保存标准问题、审核答案、分类、关键词、来源及启用状态；仅 `enabled=1` 且内容与来源有效的条目可作证据。
- 初期一条 FAQ 作为一个知识块，以实际 FAQ ID 标识；检索文本/上下文组织不能丢失答案与原始来源的关联。
- 当前 5 条资料见 `FAQ_DATA_REVIEW.md`；来源核对不等于校方官方英文译文，不自动证明当前仍有效，实施时检查日期和适用范围。
- 文档/网页分块和自动导入不是本版前置；以后增加时再定义文档 ID、块 ID、来源版本和审核流程。
- TF-IDF 基线使用统一词表、IDF 和真实 cosine；当前 0.35 只是未校准默认值。R1 Top-K 最多 3 个候选，按相关性排序，同分较小 FAQ ID 优先。
- 阈值通过独立问题集确定，不能照搬 TF-IDF 的 0.35 作为 embedding 阈值，也不能只取 Top-K 而取消无匹配判断。
- R1 已实现的证据门槛：正数 FAQ ID、enabled=true、非空白问题/答案/来源标题、无账号信息的绝对 http(s) CCNU 域名 URL（根域或子域，拒绝伪后缀）。先过滤再排序，不联网抓取或自动证明网页仍有效；当前五条资料的人工核对见数据记录。
- R1 上下文预算：最多 3 条，每条 question + answer 合计不超过 2000 个 UTF-16 代码单元，总计不超过 6000。保留完整问题，答案按剩余空间截断到副本，不拆分代理对；若问题耗尽预算或截断后无有效答案则剔除。ID、来源和更新时间保留，不修改原实体或数据库，HTTP 标准答案仍完整返回。来源元数据和将来的提示词不计入该内容字符预算，R2 必须再按所选模型限制计算整个请求的实际 token 预算；当前没有模型，尚未验证 token 上限。
- 内部接口为 `FaqService.retrieveContexts(String)` → `List<TfIdfRetriever.Match>`；Match 保留检索分数，entry 是有界知识副本。Retriever 的 `findTopMatches(String,List<FaqEntry>,int)` 仅返回正分候选，按分数降序/ID 升序，limit<=0 返回空；阈值仍在 Service 应用。保留 `findBest` 入口，无正分时返回 entry=null、score=0。
- 语义检索阶段需确定模型、维度与版本；语料修改、禁用/删除、模型变更后重建/失效，不能混用旧向量。小规模可采用 Java 内存索引；持久化结构另行审查，不在本次创建表或索引。
- 英文输出是交付约定；跨语言输入/检索只有经过对应模型与样本验证后才可宣称支持。

## 5. Prompt、生成与引用

输入包含固定系统规则、问题和明确分隔的知识上下文。检索内容不是可执行指令，不携带密码、Cookie、Session 或用户实体。

系统规则要求：仅依据给定资料回答；区分适用学年和资料版本；不能补造日期、收费、电话、链接或审批规定；资料不足时明确说明。提示词本身不能保证模型完全遵守，必须配套校验与评估。

模型输出结构约定为 `answer`（非空文本）和 `citedFaqIds`（所提供证据中的 FAQ ID 列表）；回答中的引用标记使用 `[FAQ:12]` 形式并与列表一致。模型不能提供或覆盖来源 URL。

后端须检查：结构有效、未截断、答案非空、至少一个引用 ID、ID 属于本次提供的上下文、正文引用与 ID 列表一致。验证失败不将内容显示为生成成功，来源列表由真实数据库记录构建。以上自动检查仅检查可追溯性，不能替代人工事实核对。

R3 另拒绝生成正文中常见 URI、www/裸域名、相对/Markdown/HTML 链接及 javascript/data/mailto 表示，命中时降级，导航只使用数据库来源。此保守检查可能连同文件名/邮箱式文本一并拒绝；完整标准答案不会被删改。检查不能证明事实正确，也不保证识别所有混淆文字，真实模型仍须独立评估。

## 6. 模型配置和请求预算（客户端/编排已实施；真实联调待后续）

| 配置 | 后续约定 |
| --- | --- |
| `faq.llm.enabled` / `FAQ_LLM_ENABLED` | 默认 false；开启才允许真实生成调用 |
| `faq.llm.base-url` / `FAQ_LLM_BASE_URL` | 待选定服务；可信后端 HTTPS 地址，禁止客户端覆盖 |
| `faq.llm.api-key` / `FAQ_LLM_API_KEY` | 仅环境变量或私有运行配置，无仓库默认密钥 |
| `faq.llm.model` / `FAQ_LLM_MODEL` | 待选定具体模型标识，联调时按官方文档核对 |
| 模型连接 / 读取预算 | 目标分别 3 秒 / 30 秒，整次后端请求预算 35 秒 |
| FAQ 浏览器请求超时 | 目标 45 秒，仅 FAQ 请求覆盖现有全局 5 秒默认值 |
| 生成输出预算 | 每次 512 输出 tokens；默认 max_completion_tokens，可显式改 max_tokens |
| `faq.llm.output-token-parameter` / `FAQ_LLM_OUTPUT_TOKEN_PARAMETER` | 仅允许上述两个值；默认 max_completion_tokens，不自动切换重试 |
| 请求/响应字节上限 | 整个序列化 JSON 32768 / 响应体 65536 字节 |
| 调用次数 | 每次提问最多一次生成请求，初版不自动重试 |

FaqLlmProperties 已读取上表属性及显式下划线环境变量别名；无默认地址/Key/model。启用但必要配置缺失/非法时启动失败且消息脱敏；关闭时无需密钥。基地址为可信 HTTPS（例如服务文档中的 /v1 基地址），客户端只追加 /chat/completions，拒绝 userinfo/query/fragment、路径转义和点段；禁止重定向，无自动重试。

R3 的 FaqRequestRunner 已给 HTTP 问答业务等待设置默认 35000ms 截止，包含检索与生成，不包含浏览器传输。`faq.request-timeout-ms` 允许 1–35000，启动时校验；最多四个任务且无队列，满载返回既有脱敏 503。截止前已取得可靠标准答案时返回 extractive，否则 503，不能伪装 no_match。取消和过期检查覆盖检索后、发模型前、分段读取与返回前；socket 连接/读取分别最多 3 秒/30 秒，并按剩余预算缩短。取消是协作式，阻塞 JDBC/DNS/网络任务可能延后退出，但任务容量始终有界，不承诺上游停止计费。C4/R5-B 已将 FAQ 浏览器请求单独设为 45 秒，全局仍为 5 秒。字节预算不等于 token：未选具体模型，真实联调前须核验 tokenizer、上下文窗口、JSON 模式与输出参数支持。未来 C5 允许必要时一次改写（128 输出 tokens）加一次生成（512），共用 35 秒，当前 C2 仍最多一次生成。embedding 单独选型。

## 7. API 合同：R3 与 C4/R5-B 页面已实施

保留 `POST /faq/ask`，请求 `{"question":"..."}`。浏览器 `/api/faq/ask`，模块请求工具写 `/faq/ask`。Session 的 `User`、`Identity` 必须存在，允许 `stu`、`dormManager`、`admin`，不信任客户端身份。

保留输入约束：字符串，Unicode trim 后 1–1000 个 UTF-16 代码单元；拒绝缺失、空值、非字符串、损坏 JSON、尾随内容或第二根值。保留 HTTP 400/401/403 及现有 `FAQ_INVALID_QUESTION`、`FAQ_UNAUTHENTICATED`、`FAQ_FORBIDDEN`；数据访问异常保持 HTTP 503、`FAQ_UNAVAILABLE`，对外英文且脱敏。

成功仍是 HTTP 200、`code="0"`、`msg="Success"`。下表字段已在 R3 DTO 与编排实现；真实模型验收仍待后续：

| 字段 | 约定 |
| --- | --- |
| `matched` | 是否有足够相关资料支持此次结果，不代表正确概率 |
| `answer` | 生成文本或摘录标准答案；无匹配时 null |
| `faqId`, `sourceTitle`, `sourceUrl` | 保留兼容；代表 `sources` 首项，不代表它支持所有生成内容；无匹配为 null |
| `score` | 首项来源对应的检索分数；无来源为 0，不能解释为生成置信度 |
| `guidance` | 无匹配时保持原英文指引；其他成功结果 null |
| 新增 `mode` | `generated` / `extractive` / `no_match` |
| 新增 `sources` | 实际引用的去重来源，结构为 `{faqId,sourceTitle,sourceUrl}`；无匹配为空数组 |
| 新增 `notice` | 正常生成为 null；降级时为明确的英文说明，不返回原始模型异常 |

三种成功结果：

- `generated`：真实调用成功并通过校验，matched=true，answer 为生成文本，sources 只含实际引用的证据，按其检索次序排列。
- `extractive`：模型关闭/不可用/异常/输出不合格，但存在满足阈值和来源要求的可靠 FAQ；返回最高分标准答案和对应单条来源，matched=true，notice=`AI generation is unavailable. Showing the stored FAQ answer.`。
- `no_match`：空库、低相关或无足够可用证据（TF-IDF 模式下还包括全未登录词；语义模式按自身阈值判断），matched=false，answer/兼容来源字段为 null，sources=[]，score=0，guidance=`No matching answer was found. Please contact student support.`，notice=null。不调用模型编造内容。

**R3 已实施并测试的兼容性变化：** 无匹配统一 score=0；matched=true 的 generated 可为基于资料的释义，extractive 始终保留完整标准答案。兼容 faqId/sourceTitle/sourceUrl/score 来自实际引用列表首项，未引用的最高分条目不能占用它们。sources 按本轮检索顺序、去重映射真实记录；只读一次知识快照，原实体/答案不被模型上下文截断改变。

## 8. 异常、费用与数据边界

模型关闭、运行期鉴权失败、超时、限流、非成功响应、空答案、截断、损坏 JSON、未知引用或正文引用不一致均不伪报生成成功；有可靠 FAQ 时 extractive，否则 no_match。开启但启动配置不完整仍按第 6 节启动失败，不混作运行期降级。数据库失败仍是 503，不能伪装成正常无匹配。模型限流与应用自身限流要区分，不泄露上游原始错误。

当前 R3 仅问题与必要公开知识片段发送至已配置服务；不发送个人账号资料、凭据、Cookie 或历史对话。未来 C5 的必要有界历史仅按 FAQ_CHAT_PLAN.md 用于理解/改写，不能作事实证据。API Key 不进前端、仓库、截图或日志；日志只记录必要的耗时、模式和脱敏错误类型。收费与配额以实施时所选服务规则为准，真实联调前确认模型和调用预算，不在单元测试中产生真实付费请求。

不授予模型 SQL、Shell、外网工具或业务写入能力；用户和来源内容中的提示注入不能改变这些边界。
